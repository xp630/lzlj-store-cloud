## Context

系统当前支持账号密码登录，用户名+密码方式。用户提出需要增强登录安全，在账号密码基础上增加短信验证码二次验证。

验证码发送由第三方短信服务商处理（暂不集成），但验证码校验逻辑需要自主实现。验证码存储在数据库表中。

## Goals / Non-Goals

**Goals:**
- 短信验证码写入数据库
- 提供验证码发送接口
- 支持双重验证登录（密码+短信验证码）
- 账号默认就是手机号
- 通过系统参数配置白名单，白名单账号传入 `smsCode=0000` 可跳过短信验证
- SaaS 和 LZLJ 两个模块实现相同功能

**Non-Goals:**
- 不集成实际短信发送（第三方短信服务）
- 不实现图形验证码
- 不实现注册功能
- 不实现找回密码功能

## Decisions

### 1. 验证码存储位置

**决定**: 数据库表 `sms_code`

**理由**:
- 用户明确要求存储数据库
- 相比 Redis，数据库更易于查询统计和审计
- 量级可控，不需要高性能缓存

### 2. 验证码生成策略

**决定**: 6位纯数字，随机生成

**理由**:
- 6位数字 = 10^6 = 1,000,000 种组合
- 足够防暴力破解
- 短信通道支持

### 3. 验证码有效期

**决定**: 5分钟

**理由**:
- 常规短信验证码有效期
- 太短用户体验差，太长安全性降低

### 4. 验证码使用策略

**决定**: 一次性使用，验证后标记已使用

**理由**:
- 防止重放攻击
- 验证码泄露后只能使用一次

### 5. 双重验证登录流程

**决定**: 密码验证成功后，再验证短信验证码

**流程**:
```
POST /user/login
{
  username: "13800138000",  // 账号=手机号
  password: "xxx",
  smsCode: "123456"        // 短信验证码
}

Step 1: 验证密码
Step 2: 查询系统参数 sms_login_whitelist
Step 3: if (白名单包含该手机号 && smsCode == "0000") {
            // 跳过短信验证
         } else {
            // 验证短信验证码
         }
Step 4: 返回 token
```

**理由**:
- 先验证密码确保账号归属
- 白名单机制照顾特殊用户需求
- `0000` 作为跳过标记，简单明确

### 6. 白名单配置

**决定**: 通过系统参数 `sms_login_whitelist` 配置

**参数 Key**: `sms_login_whitelist`
**参数 Value**: 逗号分隔的手机号列表，例: `13800138000,13900139000`

**理由**:
- 复用现有系统参数机制
- 无需新建配置表
- 管理员可动态修改

### 7. 登录方式演进

**决定**: 保持单一登录接口

**理由**:
- 减少接口数量
- 前端统一调用入口
- 通过参数组合区分不同场景

## Risks / Trade-offs

[Risk] 验证码明文存储 → Mitigation: 存储时加密，或限制查询权限

[Risk] 无频率限制可能被滥用 → Mitigation: 后续加接口限流

[Risk] 0000 作为白名单跳过码可能泄露 → Mitigation: 白名单仅包含可信用户，且短信验证仍可选择启用

## Migration Plan

1. 执行数据库迁移脚本，创建 `sms_code` 表
2. 配置系统参数 `sms_login_whitelist`（可选）
3. 部署 SaaS 和 LZLJ 服务
4. 验证发送验证码接口
5. 验证双重验证登录流程（普通用户）
6. 验证白名单跳过功能
7. 无需回滚（仅新增接口和表）
